## 阶段 D：RAG 检索基础（✅ 已完成）

**目标**：实现商品语义检索，调好召回质量。**先不碰 LLM 生成，只做检索 → 返回列表**。

### D.1 学习内容
- **Embedding 本质**：把文本映射为高维向量，语义相近的文本向量距离近
- **向量相似度**：余弦相似度 / 点积，理解为什么用 cosine
- **Chroma 数据模型**：
  - `Collection`：类似数据库表，存一类向量
  - `Document`：原始文本
  - `Embedding`：向量
  - `Metadata`：结构化字段（如 `price`、`category`），支持过滤
  - `id`：唯一标识
- **召回质量评估**：人工标注一批 query，看 top-K 命中率

### D.2 做什么
1. 选定 Embedding 服务（智谱 / 通义千问，免费额度够用），封装 `embedding_client.py`。
2. 设计商品向量化内容：`标题 + 描述 + 分类 + 成色` 拼成文本，避免只向量化标题。
3. 写同步脚本 `sync_products.py`：
   - 从 MySQL 读商品（先全量，上架状态）
   - 调 Embedding API 向量化
   - 写入 Chroma，metadata 存 `price`、`category`、`seller_id` 等
4. 实现 `POST /agent/search`：
   - 入参：自然语言 query + 可选过滤条件
   - query 向量化 → Chroma 检索 top-K → 返回商品列表
5. 准备测试 query 集（考研平板 / 便宜显示器 / 200 自行车…），人工评估召回。

### D.3 验证（关键，决定后续 agent 质量）
- 用"考研用的平板"检索，结果是否含性能本/平板（语义理解）
- 用"便宜显示器"检索，是否返回低价显示器
- 对比关键词搜索，语义检索在模糊意图下是否更准
- top-K 命中率记录下来，作为基线

### D.4 产出
- 商品向量库（Chroma）
- 同步脚本
- `/agent/search` 接口
- 召回质量基线数据

### F.1 为什么用 LangGraph 而非当前固定流程
- 当前两轮 LLM 流程对"多轮追问、多次工具调、路由到不同 Agent"不灵活
- LangGraph 用**状态机 + 图**建模 agent，每个节点是一个处理步骤，边是条件转移
- 天然支持多 agent 协作（阶段 G 会用），状态可在 agent 间显式传递
- 简历写"基于 LangGraph 的多智能体编排"比"写了个 if-else 流程"专业一档

### F.2 学习内容
- **StateGraph**：图的容器，定义状态结构（TypedDict）
- **Node（节点）**：一个函数，接收状态、返回状态更新
- **Edge（边）**：普通边（A→B）/ 条件边（根据状态决定去哪）
- **Checkpointer**：状态持久化，支持中断恢复
- **ToolNode**：专门执行工具调用的内置节点

### F.3 导购 Agent 状态机设计（待上 LangGraph）

```
                    ┌─────────────┐
        用户消息 →  │ understand  │  理解意图 / Query Rewrite
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │  retrieve   │  RAG 语义检索（复用 D 能力）
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │ tool_call   │  LLM 决定是否调工具（复用 E 能力）
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │ tool_exec   │  执行工具，结果回灌
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │   reason    │  综合检索+工具结果，生成 4 步推荐
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │  respond    │  流式输出 + 更新 Memory
                    └─────────────┘
```

- `understand`：多轮场景新增 Query Rewrite 子步骤（单轮直接过）
- `retrieve` / `tool_exec`：复用现有的 Chroma + 9 参数工具逻辑
- `tool_call` → `tool_exec` 是条件边：还要调工具就继续，否则去 `reason`
- `respond`：流式 + Memory 写入，Checkpointer 持久化会话

## 阶段 G：多智能体协作 + MCP（AI 线进阶 · 重点）

**目标**：构建多 agent 协作闭环，封装 MCP Server。

### G.1 多智能体协作

**学习内容**
- 多 agent 状态传递：共享 State 还是消息传递
- Supervisor / Orchestrator 路由模式：一个调度 agent 决定把任务交给谁
- Handoff 机制：agent 之间如何移交控制权

**做什么**：加**议价 Agent**，构建"导购 → 议价"协作闭环。
- 议价 Agent 能力：参考同类均价（RAG）+ 双方信用评分，在合理区间协助协商
- LangGraph 编排：导购 Agent 完成推荐后，若用户表达议价意图，supervisor 路由到议价 Agent
- 议价 Agent 完成后结果回传，导购 Agent 整合输出

**协作链路示例**
```
用户："找辆 200 以内的自行车，帮我砍到 180"
   ↓
导购 Agent：检索 → 推荐"捷安特 200 元"
   ↓ (用户：帮我砍到 180)
Supervisor 路由 → 议价 Agent
   ↓
议价 Agent：查同类均价(180-220) + 卖家信用 → 建议出价区间
   ↓
返回协商建议
```

**验证**：上述链路端到端跑通，agent 间状态正确传递。

### G.2 MCP Server 封装

**学习内容**
- MCP（Model Context Protocol）协议：Anthropic 提的标准，"AI 世界的 USB 接口"
- Server / Tool / Resource 模型
- 为什么 MCP 比自定义工具接口更通用
